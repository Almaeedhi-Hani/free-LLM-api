# الخطة الشاملة — تشغيل تلقائي كامل + توحيد لوحة التحكم + شاشة روابط المحتوى المنشور

- **حالة المستند:** خطة معتمدة للتوثيق؛ التنفيذ مشروط ببوابات المراحل وبموافقات المالك المحددة أدناه.
- **تاريخ بدء التوثيق:** 2026-11-19 (Asia/Riyadh).
- **مرجع التصنيف:** تقرير تدقيق لوحة V3؛ V01–V18 للشاشات، B01–B15 للأدوات، W01–W08 للـ workflows، D01–D13 للبيانات. لا تبدأ جردًا جديدًا إلا للتحقق من التغيّر الفعلي.
- **سجل التنفيذ الملزم:** docs/plans/PROGRESS.md؛ يحدث بعد **كل مرحلة** مع الحالة والتاريخ وPR ودليل بوابة الخروج.
- **نمط التنفيذ الافتراضي:** **النمط أ**: مرحلة واحدة ثم تقرير نقطة تفتيش وموافقة المالك قبل التالية. لا تعتمد النمط ب إلا برسالة تشغيل صريحة من المالك.
- **أسبقية التعليمات:** احترم root AGENTS.md وdocs/v3-multi-agent-execution.md والسياسات الإنتاجية القائمة. أي تعارض يستلزم عرضًا للمالك، لا تعديلاً صامتًا.

## 0. الأهداف

1. **تشغيل تلقائي كامل:** لا يتدخل المالك إلا في الاستثناءات (القسم 9).
2. **لوحة صغيرة بلا تكرار:** كل الأدوات القديمة المتكررة أو المعطلة في أرشيف واحد، وكل أداة تظهر مرة واحدة.
3. **شاشة روابط المحتوى المنشور فقط:** تنقل عرض الروابط القائمة في اللوحة ولا تعيد بناءه.

## 1. القواعد الحاكمة غير القابلة للتجاوز

1. لا تغيّر سياسة النشر الآلي ولا حد النشر الحالي **3**. يقرر المالك التغيير بنفسه.
2. لا تحذف الجداول أو البيانات. الترحيلات **additive** فقط؛ افحص الجداول قبل أي إنشاء (بما فيها geo_agent_feedback وgsc_sync_day_outcomes وgsc_daily_metrics) وأعد استخدامها.
3. لا تحذف كودًا قبل مراقبة دورة كاملة، وفقط في المرحلة 8 بشروطها.
4. أدوات مجانية فقط طبق سياسة SEO/GEO. لا تُجرب مزودين خارجيين باستهلاك حصص.
5. لا تطبع أسرارًا أو قيم متغيرات البيئة؛ الأسماء وحالة وجود الإعداد فقط.
6. **فرع وPR مستقل لكل مرحلة**. قبل كل مرحلة وسم Git بصيغة pre-<phase>-YYYYMMDD. اجتز CI + اختبارات القبول + Evals قبل الدمج.
7. أي إخفاء واجهي لأداة قديمة خلف feature flag قابل للتراجع الفوري.
8. لا تنتقل إلى مرحلة قبل نجاح وتوثيق بوابة خروج السابقة في PROGRESS.md. عند الفشل: توقف وأبلغ.
9. وسم جميع الأحكام: **مؤكد / مستنتج / غير معروف**.
10. لا تغير سياسات النشر/المخاطر أو أدوار التصاريح أو أسعار الموقع ضمن أعمال التنظيم.
11. أي تغيير يحتاج مراقبة إنتاجية حقيقية لا يُعد ناجحًا بالاختبارات أو GitHub Actions وحدها.

## 2. نمطا التنفيذ

- **النمط أ — الافتراضي:** نفذ مرحلة، أرسل تقرير نقطة تفتيش، وانتقل التالية بعد الموافقة.
- **النمط ب:** نفذ بالتتابع دون موافقة بين المراحل **لكن** لا تتجاوز بواباتها، وتوقف عند أي فشل.
- البوابات التي تحتاج دورة schedule حقيقية أو 30 يومًا لا يمكن اختصارها؛ يجوز تجهيز PR لاحق **دون دمجه** حتى تمر السابقة.

## المرحلة 0 — التحضير والسلامة

1. احفظ هذه الخطة وأنشئ PROGRESS.md.
2. ضع وسم Git الحقيقي **pre-consolidation-YYYYMMDD** عند commit البداية على main.
3. احفظ لقطة أساس: V01–V18 والتبويبات؛ كل /api/admin/* و/api/geo/*؛ جميع workflows وجدولها؛ أعداد صفوف الجداول الرئيسية.
4. تحقق من نجاح CI على commit main المرجعي.
5. دوّن القرارات المعلقة (القسم 10) في PROGRESS.md.

**بوابة الخروج:** الوسم موجود، اللقطة محفوظة، CI أخضر. إذا لم يمكن إنشاء وسم حقيقي، لا تعتبر فرعًا بديلًا للوسم ولا تتقدم.

## المرحلة 1 — موثوقية التشغيل التلقائي الحالي

### 1.1 GSC: W04 / B06 / D07

- أزل أي اعتماد على ساعة التنفيذ الفعلية (مثل getHours)، واعتمد على بيانات الأيام المفقودة.
- استخدم gsc_sync_day_outcomes الموجود، بالتصنيف: success_with_data / success_no_data / failed.
- غياب الصفوف ليس فشلًا، وأعد فحص success_no_data بعد **3–7 أيام** بسبب التأخر.
- سدّ الفجوة من آخر يوم قياس **15 نوفمبر 2026** حتى **اليوم − 3**، وفعّل بُعد الصفحة.
- لا تصادق على النجاح إلا بحفظ فعلي في Supabase وتواريخ وعدد صفوف.

### 1.2 GEO: W01 / B03

- أثبت عمل إصلاح PR #156 بدورة **event=schedule** فعلية. انتظر الجدولة التالية.
- إذا تجاوز تأخرها ساعتين، يجوز workflow_dispatch واحد فقط للتحقق، مع توثيقه بوضوح، دون تسميته schedule.
- تحقق من حفظ مسودات FAQ ومقترحات editorial ومن تسجيل أسباب رفض مثل invalid_guide_slug.

### 1.3 الرادار: W02

- شخّص غياب schedule عبر cron وdefault branch وتفعيل workflow والعلم MARKET_RADAR_PAUSED وخمول GitHub.
- اذكر السبب **المؤكد** فقط وحالة وجود العلم دون قيم حساسة.
- تحقق من event=schedule ومن الحفظ في D01–D04.

### 1.4 منع تكرار النشر

- تحقق من idempotency بين النشر بعد W01 والنشر المجدول W03.
- حافظ على حد النشر الحالي كما هو (**3**) وسجلات D06، واحفظ مصدر كل محاولة.

### 1.5 صحة الصفحات الإنتاجية

- تحقق بطلبات HTTP غير معدِّلة من أن كل صفحة منشورة تُرجع 200، وسجل النتائج.

### 1.6 تحضير أمني **دون تطبيق الإنتاج**

- جهّز فقط ترحيلًا لإزالة حق EXECUTE غير المناسب لدالة public.rls_auto_enable() من anon وauthenticated، وتثبيت search_path للدالة public.geo_set_updated_at().
- لا تطبقه على الإنتاج دون موافقة المالك، ولا تفتح سياسات RLS الخاصة.

**بوابة الخروج:** لكل W01–W06 تشغيل schedule ناجح واحد على الأقل **ودليل الحفظ الفعلي المرتبط** (أرقام وتواريخ). لا تنسب كتابة رادار مرتين للتشغيل نفسه. جدول الأدلة يُحفظ في PROGRESS.md. بالنسبة للمهام التي لا يُفترض أن تكتب صفوفًا في كل دورة، سجّل دليل نتيجة العمل الفعلية أو قرار no_change الموثق بدل اختلاق صفوف.

## المرحلة 2 — شبكة الأمان: إنذارات وتقرير وإيقاف وحصص

### 2.1 Watchdog

- workflow مجدول كل **6 ساعات** يفحص GitHub API عن آخر schedule ناجح لكل W01–W06 ومقارنته بالفاصل المتوقع.
- إن مرّ أكثر من **ضعف الفاصل** يفتح/يحدّث GitHub Issue بوسم watchdog وعنوان ثابت لمنع التكرار.
- يقارن كذلك آخر حفظ حقيقي في الجداول المرتبطة؛ نجاح workflow وحده لا يكفي.

### 2.2 إنذار فشل workflow

- خطوة if: failure() في كل workflow إنتاجي، تفتح/تحدث Issue بوسم failure دون تكرار. تصل إشعارات GitHub للمالك.

### 2.3 تقرير أسبوعي واحد

- workflow أسبوعي ينشر Issue بوسم weekly-report، ويُعرض ملخصه في الرئيسية.
- يشمل W01–W06 ونتائج الحفظ؛ الكلمات المقبولة/المرفوضة؛ Evals؛ فرص GSC **المقاسة إن توفرت**؛ AI visibility الفعلي مع حجم العينة منفصلًا عن model_only؛ حصص المجاني؛ القرارات المعلقة.

### 2.4 إنذارات الجودة

- إنذار Issue عند ظهور رابط منافس في نص صفحة عامة أو cited_sources، بناءً على فحص دوري.
- إنذار عند فشل أي حالة Evals.

### 2.5 Master Pause

- مفتاح واحد لجميع workflows الإنتاجية، يوحد الأعلام الحالية MARKET_RADAR_PAUSED وAUTODEV_PAUSED وLLM_INDEX_PAUSED تحته بدل إنشاء نظام إيقاف ثانٍ.
- زر واحد في اللوحة؛ تخزين آمن قابل للتحكم مثل الإعدادات الموجودة.
- لا تُوسّع GitHub token scopes لتعديل GitHub Variables من واجهة الموقع. إن استلزم الأمر ذلك، اعرض البديل على المالك قبل التنفيذ.

### 2.6 حارس الحصص المجانية

- حدود يومية لكل مزود، توقف آلي عند **80%** مع quota_reached مسجل.
- اتبع أولويات سياسة الأدوات المجانية ولا تلتف على الحصص.

**بوابة الخروج:** محاكاة آمنة لكل إنذار دون تأثير على الإنتاج، وإثبات وصوله؛ إنتاج التقرير الأسبوعي مرة بنجاح.

## المرحلة 3 — بوابات آلية بدل الاعتماد اليدوي

**قيد:** سياسة النشر الحالية كما هي؛ الفاشل إلى needs_review ويظهر بالتقرير الأسبوعي دون إيقاف خط الإنتاج. أي تعارض مع المراجعة البشرية الإلزامية في AGENTS.md يُعرض للمالك ولا يُتجاوز.

1. **فصل المنافس عن المرجع الرسمي:** تحقق من PR #142 أولًا؛ إن لم يكتمل، استخدم قائمة المنافسين الديناميكية من Supabase مع fallback، وفحص cited_sources وsource_urls ونص المقال، وفلتر insights/[slug] واختبارات. لا تغيير للسياسة.
2. **ملاءمة الكلمات:** قبول/رفض تلقائي مع reason، وفئة out_of_scope_review للشعارات والعلامات التجارية دون حظر دائم؛ ar/en/zh؛ cleaning report would_remove قبل التغيير.
3. **مسودات FAQ وeditorial V10/V11:** بوابات بنية، منافسين، لغة، منع تكرار، Evals، وتصنيف مخاطر ملتزم بالسياسة. الصالح يُعتمد وفق السياسة الحالية، والفاشل needs_review.
4. **الفرص والأهداف V05/V06:** قواعد حتمية للظهور والمركز والعمر، تسجل أسبابًا قابلة للتراجع.
5. **المهام التقنية V05/B13:** GitHub Issues آلية بحد أقصى يومي ومنع التكرار.
6. **تصحيحات geo_agent_feedback:** يقترح الوكيل قاعدة عامة، لا تفعّل إلا باعتماد المالك الأسبوعي؛ Evals قبل كل نشر، وتفشل المهمة عند أي حالة فاشلة.
7. **قياس AI عبر Gemini:** measurement_type منفصل بين model_only / search_grounded / manual_ai_search، دون خلط أو اعتبار model_only دليل ظهور فعلي.
8. **عينة أسبوعية بعد النشر:** 3 صفحات أسبوعيًا مع اهتمام بالمحتوى القانوني والاستثماري؛ تفعيلها ينتظر قرار المالك.

**بوابة الخروج:** وحدة وقبول لكل بوابة ودورة كاملة تُثبت قبولًا ورفضًا، ولا رابط منافس في أي صفحة عامة مرئية.

## المرحلة 4 — الأرشيف الموحد «أدوات قديمة / أرشيف»

- شاشة واحدة مطوية افتراضيًا، لا تظهر في التنقل الرئيسي ولا تتكرر أدواتها.
- التحقق ثم النقل: B15 (كلمات content_store القديمة)؛ V04 (التوصيات المؤقتة بعد نقل الحفظ إلى V05)؛ B08/D08 (نموذج AI السابق مع إبقاء التاريخ مقروءًا)؛ أزرار الرادار والتحليل السابقين في V07؛ أي عناصر UI لـ cron-agent أو cron-unified أو orchestrator/worker القديم؛ روابط V18 فقط؛ أي تكرار إضافي مثبت.
- لكل أداة: اسمها، سبب الأرشفة، بديلها/رابطه، وآخر استخدام مثبت أو «غير معروف».
- **لا حذف للكود أو API أو الجداول.** إخفاء مواضع الواجهة الأصلية خلف feature flag قابل للتراجع؛ موضع واحد للأداة داخل الأرشيف.
- احتفظ بطبقة adapter واحدة بين الشاشات والخدمات؛ الأرشيف للقراءة والتشخيص لا للتشغيل اليومي.

**بوابة الخروج:** لقطة التنقل الجديدة بلا تكرار، عدّ ملفات الـ API والجداول دون نقصان، واختبارات القبول خضراء.

## المرحلة 5 — شاشة جديدة «المحتوى المنشور: الروابط»

**نقل لا إنشاء من جديد، ولا أزرار تشغيل ولا إحصاءات ولا إعدادات.**

1. ابحث ودوّن مواضع روابط المنشور والمعاينة الموجودة: V09 وV10 وV11/V12 وV08 وD06 (ملف/مكوّن/سطر).
2. استخرج الأكمل إلى مكوّن مشترك PublishedLinksList، مع دمج الميزات المفقودة من النسخ الأخرى.
3. انقل الروابط إلى الشاشة، واستبدل النسخ السابقة برابط صغير «عرض في شاشة الروابط» خلف علم قابل للتراجع. لا تكرر القائمة.
4. استخدم content_store وgeo_publication_events وأحداث FAQ الموجودة؛ **لا جداول جديدة**.
5. تعرض قائمة المنشور المؤكد: العنوان واللغة (ar/en/zh) والنوع وتاريخ النشر والرابط العام ومصدر النشر (آلي/يدوي)، مرتبة من الأحدث وبحث وتصفية لغة.
6. روابط المعاينة المنشورة بجانب عنصرها؛ معاينات غير المنشور في مجموعة ثانية مطوية «معاينة مسودات»، ولا تخلطها بالمنشور.
7. للإدمن فقط؛ متوافقة مع الهاتف، وروابط قابلة للنقر. فحص HTTP في المرحلة 2 لا في هذه الشاشة.
8. أضفها في التنقل الرئيسي كتبويب مستقل.

**بوابة الخروج:** عدد العناصر المنشورة في الشاشة = عدد العناصر المنشورة المؤكد في القاعدة، جميع الروابط تُرجع HTTP 200، لا نسخة قديمة للعرض، واختبار واجهة ناجح. إذا وجد اختلاف في تمثيل FAQ أو روابط افتراضية، سجّل السبب ولا تخترع صفحات منشورة.
